# 数据库设计审核要求

## 1. 物理-数据库表设计审核

| 审核项 | 审核要求 |
| --- | --- |
| 主键 | 建表必须要有主键，并推荐使用自增 id 作为主键。部分数据库表没有主键会导致主从复制延迟问题，自增 id 可避免记录的顺序和主键插入的顺序不一致，减少磁盘的随机读写。 |
| 编码 | MYSQL/TXSQL 数据库建议统一使用 UTF8MB4 字符集编码。 |
| 字段名 | MYSQL/TXSQL 数据库所有表名及字段名尽量不超过 32 个字节，最大不能超过 64 个字节。 |
| 外键 | 建议不要使用外键约束。外键虽然可以保证数据的准确性、参照完整性，但每次进行写操作时都会走校验数据是否正确的流程，会有损写操作的性能，数据的参照完整性建议在业务层实现。 |
| 字符集 | 建数据库时或者需要关联的库中所有表的字符集和校验字符集建议保持一致，避免索引失效。MYSQL/TXSQL 数据库校验字符集及连接校验字符集建议设置为 utf8_general_ci，服务端校验字符集设置为 utf8mb4_bin。 |
| 存储引擎 | 使用存储引擎时需在建表语句中明确指定，如 MYSQL/TXSQL 数据库表必须使用 InnoDB 存储引擎且在建表语句中明确指定，建表语句中必须明确写出 `ENGINE=InnoDB`。 |
| 文件对象 | 对于支持文件对象的存储数据库，会占用数据库很大的存储空间。在数据库中的读写会消耗内存和占用大量的 I/O 流，最终导致查询的效率低下，尽量不在数据库中存储文件对象。 |

## 2. 物理-数据库字段设计审核

| 审核项 | 审核要求 |
| --- | --- |
| 三最原则 | 字段命名、数据类型等在符合数据标准原则基础上，在物理模型设计上可以遵循“三最”原则，即字段长度遵循最合适（选择最合适的数据类型存储不同数据）、最完整（确保定义的数据类型长度可以存储完整的业务数据不会截断）、最简短（确保能用占用字节更少的数据类型存储完整数据）的“三最”原则。 |
| 字段名 | MYSQL/TXSQL 数据库所有表名及字段名尽量不超过 32 个字节，最大不能超过 64 个字节。 |
| 空值 | 字段尽量添加 NOT NULL 属性并设置默认值。 |
| 字段类型 | 1. 在满足需求的情况下，使用占用空间少的类型可以减少存储空间和提升性能，如 MYSQL/TXSQL 数据库存储人数时使用 UNSIGNED 存储非负整数。<br>2. MYSQL/TXSQL 数据库适当使用 VARCHAR 替代 CHAR 类型，VARCHAR 存储可变长字符串，字符串是变长时，VARCHAR 更节约空间，而 CHAR 是定长，即使字符未存满，申请的空间长度也会提前分配。<br>3. MYSQL/TXSQL 数据库字段数据包含小数时尽量使用 DECIMAL 类型而不使用浮点型。<br>4. MYSQL/TXSQL 数据库尽量使用 DECIMAL 替代 FLOAT/DOUBLE 类型。DECIMAL 类型为精准浮点数，在计算时不会丢失精度，可以自定义其长度，可用于存储比 BIGINT 更大的整型数据。 |
| 字段数量 | 单表不建议有过多字段，建议控制在 30 个以内。在针对同一行不同的 SQL 修改不同的字段时，影响被放大，MYSQL/TXSQL 的锁粒度到行级别，即使选择的是同一行完全不交叉的列，也会相互影响。太多的字段考虑垂直拆表。 |

## 3. 物理-数据库索引设计审核

| 审核项 | 审核要求 |
| --- | --- |
| 性能 | 1. 要创建索引的字段需要选择性较强、区分度较高，字段值需要唯一性较高。如果选择性不高，在极端性情况下可能会扫描全部或者大多数索引，然后再回表，这样反而增加了 I/O 的消耗。<br>2. 严格限制在索引列使用函数和运算，避免在 WHERE 子句中查询条件左侧字段上使用函数，而是在查询条件右侧常量上使用函数或其它方式实现。WHERE 子句中字段使用函数，则无法使用字段上的索引优化性能。如不允许使用：`max(id) > 10`，`id+1 > 3` 等。<br>3. 在长度大于 50 的 varchar 字段上建立索引时，必须根据前缀长度区分度指定索引前缀长度，无需对全字段建立索引，根据文本区分度决定索引长度即可。 |
| 数量 | 单表的索引在满足业务需求下尽可能控制在 5 个以内，索引是面向读操作友好的，但是对写操作却增加了成本。每一个索引都要生成相应的索引树，占据内存空间，在更新记录时，需要更多的操作。 |

## 4. 逻辑-数据项设计审核

| 审核项 | 属性类别 | 数据项属性 | 审核要求 |
| --- | --- | --- | --- |
| 系统设计 | / | / | 各系统应在数据字典与数据模型管理系统（以下简称“数据字典管理系统”）数据模型管理功能模块中及时维护库表结构、接口文件结构；对存量库表结构、接口文件结构应及时补充更新至最新；对后续迭代变动部分应坚持“先设计、后开发”，确保设计模型与生产模型的动态一致性。 |
| 系统设计 | / | / | 系统 SA 在确定表结构/接口变更内容后，及时发起表结构/接口变更公示通知，各关联系统应根据主系统变更进行配套改造，对于影响较大的，评估确认是否提供新旧双接口文件。 |
| 数据来源信息 | / | / | 应准确维护字段的数据来源信息，字段数据来源区分为本系统采集加工、引自其它系统，对于引自其它系统字段，应进一步维护来源系统、表、字段。 |
| 数据项映射数据字典 | / | / | 1. 系统新增数据项应直接使用企业级数据字典，确保中文名称、英文简称（字段名）、数据类型、数据格式、值域等全部属性与企业级数据字典保持一致。对于无可用企业级数据字典的，原则上应先新增企业级数据字典后使用。<br>2. 系统存量数据项关联企业级数据字典的，应根据本行企业级数据字典落地指导意见逐步实现数据贯标。 |
| 数据项属性完整性 | / | / | 至少维护数据项中文名称、英文简称、数据类型以及代码值域等。 |
| 数据项唯一性 | / | / | 系统内数据项应具备唯一性，分析是否存在同名不同义、同义不同名、同义不同格式等情况。 |
| 数据项属性 | 基础属性 | 中文名称 | 中文名称是数据的统一中文命名，用于从业务上区分不同的数据，应易于被数据使用人员理解和识别，应符合唯一性、可共享性、一致性原则。中文名称应符合以下规范：<br>1. 采用“限定词术语+对象类术语+表示术语（结尾类词）”的格式进行定义的名词短语。其中，结尾类型应遵循通用规则，如：<br>（1）日期类数据项，中文名用“**日期”，时间类用“**时间”，日期时间类用“**日期时间”。<br>（2）指代自然人姓名一般用“**姓名”，指代机构名一般用“**名称”。<br>（3）区分“**OA账号”、“**客户编号”（CIF 号）、“**员工编号”（人力号）、“**人员编号”。<br>（4）区分账号和账户代号、凭证序号和凭证代号、机构编号和机构代号作为结尾词的不同含义。<br>（5）数据项逻辑数据类型应与结尾类词对应（见《企业级数据字典落地工作手册-5、字典编制规范相关说明》 https://weboffice.cib.com.cn/weboffice/l/chrgyoodsofi）。<br>2. 中文名称字数不应过长，原则上不超过 15 个汉字。中文名称字数不应过短，且需要明确表达其含义，不可以仅以表示术语（结尾类词）命名，如“编号”，需要明确表达其含义，如“客户编号”。<br>3. 中文名称中尽量避免括号、斜杠等特殊符号；对于中文名中包含单位信息的情况视具体情况分析。尽量避免使用“和、或”等连接词，如“客户联系方式和地址”应拆分为客户联系方式、客户联系地址。<br>4. 已关联数据标准的，应保持数据项中文名称与企业级数据字典中文名称一致。无关联数据标准，需新建标准的，新建企业级数据字典项的中文名称不可和公共级数据字典项以及同一字典定义机构下的自治级字典项重名。 |
| 数据项属性 | 基础属性 | 英文简称 | 数据项英文简称即系统数据库字段名，是数据项的统一英文缩写，由数据项中文名称经翻译、缩写形成。命名应当清晰、明了，具有明确含义。<br>1. 应采用英文字母和自然数加下划线组成；多个单词简称下划线“_”分割；长度不超过 30 个字符；建议小写命名，不推荐用大写。例如：Account Number 的字典项英文简称为 Acc_No，数据项英文简称建议为 acc_no。<br>（1）去掉所有元音，例：Market-mkt、Manager-mgr。<br>（2）保留前几个字母，例：Information-info、Insurance-ins。<br>（3）保留开头和结尾发音字母，例：Week-wk、Room-rm。<br>（4）根据发音，例：Though-tho、Through-thru。<br>（5）常见行业用语组缩写单词首字母，例：Create, Read, Update, Delete-crud。<br>（6）如果已经存在缩写（国际通用、业务通用或数据字典提供），使用已存在的缩写。如常用短语，例：Return On Investment-roi。<br>（7）常用单词可以缩写为一个字母，例：True-t。<br>（8）词组中省略虚词，例：Archives Of Medical Research - arch_med_res。<br>（9）学科名称缩写，例：Chemistry-che、删除-连续同前面若干字母-chem。<br>（10）应当注意避免与数据库或程序语言保留字冲突，如：int、name、time、datetime、password 等。<br>2. 新建系统应实现全面数据标准严格落地，数据项英文简称（字段名）应与企业级数据字典英文简称保持一致（大小写除外），以满足上述要求。存量系统增量数据项建议实现数据标准严格落地，数据项英文简称（字段名）建议与企业级数据字典英文简称保持一致（大小写除外）。<br>3. 数据字典管理系统提供【命名元素】功能菜单：<br>（1）【命名元素】菜单展示中文名称对应英文名称及英文简称。对于常用英文缩写，但命名元素中尚且没有的，可整理提交对接数据标准化联系人补充。<br>（2）【命名元素】菜单中提供批量翻译功能，支持导入中文名称返回建议英文简称。<br>（3）【命名元素】内嵌设计功能，数据项设计界面、字典项维护流程中，均支持根据中文名称描述生成英文简称。 |
| 数据项属性 | 业务属性 | 业务定义 | 业务定义是对数据业务口径和相关业务场景的详细描述，是数据业务含义的自然语言表述。业务定义应符合以下规范：<br>1. 格式上：业务定义应以“指”或“描述”开头，以“。”结尾。<br>2. 内容上：<br>（1）业务定义应精准、细致，以利于数据使用人员理解，不应有循环引用或直接使用中文名称定义。<br>（2）业务定义中尽量避免出现“引自/来自/XX系统”的字样，不应从数据来源、使用系统等描述说明数据含义，应从业务场景/要求来描述。<br>（3）业务定义可以参考相关国家字典和行业字典、外部监管机构的规定、银行内部业务制度、信息系统业务需求以及行业经验的总结归纳。<br>3. 职责分工上：业务功能相关数据项的业务定义由 BA 进行补充，技术相关数据项的业务定义由 SA 进行补充。 |
| 数据项属性 | 技术属性 | 数据类型 | 数据类型是对数据字典项表现形式的分类，包括以下 10 类：<br>（1）编码类：编码类是用少量、简单的基本符号，选用一定的组合规则，表示大量复杂多样的信息。示例：客户编号、机构编号、产品编号。<br>（2）代码类：代码类是一套预先定义的，用来描述一个有限集合的事物或事物的属性，代码数据能够相对稳定的在一段时期内。示例：币种、证件类型。<br>（3）标志类：表示“是/否”意义的标志。1-是、0-否。示例：允许自动转存标志、员工标志。<br>（4）文本类：需要以文本的形式对与业务活动密切相关的对象和业务的进行说明的数据。示例：客户法定名称、交易对手地址。<br>（5）金额类：金额类指以货币金额的形式体现的数据项，适用于各类财务信息。金额类数据定义度量单位（元、万元等）。示例：注册资本、单笔资金转出限额。<br>（6）数值类：数值类指除金额类及比例类外的以整数或小数的形式体现的数据项。适用于各类以数量反映的信息。示例：机构营业面积、流通股数。<br>（7）比例类：比例类指以比值的形式体现的数据项，适用于各类比率信息。示例：资本充足率、回购利率。<br>（8）日期类：日期类指以需要日期的形式体现的数据项，以描述银行业务发生的日期。示例：出生日期、产品上市日期。<br>（9）时间类：时间类指以需要时间的形式体现的数据项，以描述银行业务发生的时间。示例：交易时间、客户创建时间。<br>（10）日期时间类：日期时间类指以需要以日期和当日时间的组合形式体现的数据项，以描述银行业务发生的日期和时间。示例：交易国际时间。 |
| 数据项属性 | 技术属性 | （逻辑）数据格式 | 数据格式是数据项在精度、长度、形态上的定义，包括所允许的最大和/或最小字符长度，数据的标识格式等。表示格式的各种符号含义如下：<br>a-字母字符，n-数字字符，an-字母数字字符，anc-字母数字汉字字符。M、N 表示自然数。<br>M... 最大为 M 位字母字符。<br>M(a) M 位字母字符，定长。<br>M(an) M 位字母数字字符，定长。<br>Manc M 位字母数字汉字字符，定长。（不同编码汉字字符可占多个字节，根据实际需要设定）<br>n... 最大为 N 位数字字符。<br>nM N 位数字字符，定长。<br>an... 最大为 N 位字母数字字符。<br>anM M 位字母数字字符，定长。<br>anc... 最大为 N 位字母数字汉字字符，（不同编码汉字字符可占多个字节，根据实际需要设定）<br>ancM M 位字母数字汉字字符，定长。<br>N(M) N 位数字字符，其中 N 个小数位（M 位），不包含小数点或其他数字字符。<br>YYYYMMDD 日期格式，表示年月日。Y 表示时间元素“年”所使用的数字，M 表示时间元素“月”所使用的数字，D 表示时间元素“日”所使用的数字。<br>HHMMSS、HHMMSS.S...S 时间数据格式，S 表示时分秒。H 表示时间元素“小时”所使用的数字，M 表示时间元素“分钟”所使用的数字，S 表示时间元素“秒”所使用的数字，小数点后 S 个数表示时间精度。SSSSS 表示毫秒。<br>YYYYMMDDHHMMSS、YYYYMMDDTHHMMSS.S...S 日期时间格式，表示年月日时分秒毫秒。<br>不允许纯数字的数据格式，例如 12。<br>比例类：只能使用 M.N）数据格式。数据格式推荐采用 M(2)、M(3)、N(4)），默认单位“%”，例如 100.00%、100.000%。<br>金额类：只能使用 M.N）数据格式。数据格式推荐采用 N(2)、N(3)、N(4)），默认单位“元、美元”等基础货币单位。<br>数值类：只能使用 M.N）数据格式，在没有小数位的情况下不允许使用 M(0)，长度为 N 的情况下不允许使用 n_。<br>代码类：建议使用 M_或 an_、anc 等定长数据格式，应根据代码取值设计数据项长度，不可预留长度。<br>日期类：只能使用 YYYYMMDD 数据格式。<br>时间类：只能使用 HHMMSS、HHMMSS.S...S 数据格式，其中小数点后 S 的个数表示时间精度。<br>日期时间类：只能使用 YYYYMMDDHHMMSS、YYYYMMDDTHHMMSS.S...S 数据格式。<br>编码类：应根据编码规则设计数据项长度，不可预留长度。 |
| 字段属性 | 技术属性 | 物理类型（字段类型） | 字段物理类型为数据库字段类型，数据项（逻辑）数据格式与字段物理数据格式存在映射转换关系。<br>1. 类型映射，详见 https://...（图片中 URL 不完整）。<br>2. 长度转换：<br>（1）编码方式与字符、字节转换问题：<br>编码方式为 UTF-8。存储 1 个中文字符一般占 3 个字节，1 个英文字符占 1 个字节；<br>MySQL 5.7 以上版本，varchar 默认单位为字符，即对于 GBK 编码，6 个中文字符需用 varchar(12)；如果是 UTF-8 编码，则需用 varchar(18)。<br>Oracle/SQL Server 默认单位为字节；GBK 编码，6 个中文字符需用 varchar(12)。<br>（3）根据数据库类型、系统字符集编码方式，确认数据项（逻辑）数据格式长度对应的字段物理格式长度。例如 MySQL 的字段标识 IP0000006 客户名称，（逻辑）数据格式为 anc...128，则可以用 varchar（128）；OpenGauss 为 UTF-8 编码的字段需用 IP0000006B 客户名称。<br>3. 数据字典管理系统中支持数据项、字段自动转换。系统维护数据项时，可进一步确认、调整转换后的字段类型，完成数据项维护与模型设计后，可通过设计模型“正向导出”功能生成 DDL 建表语句，完成逻辑格式到物理格式的转换。 |
| 数据项属性 | 技术属性 | 代码编码规则 | 代码编码规则是指代码类数据项的具体编码规则，表述为 XXX 位编码。例如：民族为 MA，1 做 2 位编码。行业分类为 ABCD3、4 做 5 位编码。“数据类型”为“代码类”时，本属性为必填项。<br>各系统应在字典系统维护系统内部的代码清单（值域）集合，并构建数据项与代码清单的关联关系。<br>1. 代码项应在“数据项定义的有限枚举项清单”的，如币种、证件类型、业务状态，应维护“数据类型”为“代码类”，并补充代码清单。中文名称应以……词结尾的，疑似为代码类。 |
| 数据项属性 | 技术属性 | 代码清单 | 2. 新增代码清单的，应遵循以下设计规范：<br>（1）代码取值一般仅包含数字字母、纯字母的，不允许使用中文字符、特殊字符；<br>（2）同一码表内，代码取值、代码名称均不应重复。<br>（3）推荐使用枚举类型、文本存储编码值，调用数值存储，不允许使用浮点数据型存储。<br>3. 登记存量代码清单的，应根据系统现状如实维护，对代码取值包含中文字符、特殊字符的，或使用数值型存储的，也应在字典系统如实登记。<br>4. 存在数据项间的引用关系时，引用数据项取值应是被引用项的全集或子集。 |
