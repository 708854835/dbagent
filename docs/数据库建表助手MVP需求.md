# 数据库建表助手（MVP）需求清单

## 1. 项目概述

1.1 建设目标：为软件开发人员提供嵌入 IDEA 的智能建表工具，在新增建表场景下自动落实本行数据库设计标准与数据贯标要求，降低手工建表的合规成本与返工率。

1.2 核心价值：开发人员只填中文业务信息，即可一键生成符合行内标准的建表 DDL；字段命名自动优先复用本系统已有定义、其次走企业标准贯标，保证一致性。

1.3 版本定位：MVP 覆盖"新增建表"场景，并含 LLM 辅助能力（详见 3.5）；存量改造、门禁、CI 等能力后续分期建设。LLM 定位为规则无法决断时的辅助补充，不作为决策主体。

## 2. 范围边界

2.1 本期范围（做）：
- 2.1.1 IDEA 插件：建表向导对话框（录入表单 + 结果预览 + 一键插入）
- 2.1.2 标准引擎：服务端 HTTP 服务（内网部署），提供 DDL 生成接口，集中管理各系统的 JDBC 连接与用户归属
- 2.1.3 规则集：数据库设计审核规范（4 张审核表）转配置化规则
- 2.1.4 双数据缓存：本系统 Schema 缓存 + 企业标准字典离线快照
- 2.1.5 新字段登记支持：生成"待登记字段清单"供数据管理员在字典系统补录（本期仅输出清单，不做自动回写）
- 2.1.6 数据库类型：本期支持 MySQL 及与其语法/物理类型兼容的 TXSQL（同属 MYSQL/TXSQL 体系），DDL 生成与类型映射按此实现
- 2.1.7 LLM 辅助能力：规则无法精确决断的环节，由 LLM 辅助解析/建议，并经过确定性规则校验（详见 3.5）

2.2 本期不做（明确排除）：
- 2.2.1 存量表的贯标扫描与改造
- 2.2.2 SQL 实时检查（inspection）与字段补全提示
- 2.2.3 Pre-commit Hook 提交门禁、CI 集成
- 2.2.4 纯 LLM 自然语言生成 DDL（LLM 作为决策主体的整体生成方式；本期仅采用"规则优先 + LLM 辅助"模式，见 3.5）
- 2.2.5 Web 门户、管理后台、字典系统实时对接
- 2.2.6 Oracle、GaussDB 等其它数据库类型支持（后续版本扩展；TXSQL 与 MySQL 同体系，本期已支持）
- 2.2.7 企业字典系统间自动联动对接（本期仅支持手动导出导入）

## 3. 功能需求

3.1 IDEA 插件（前端）
- 3.1.1 入口：主菜单/编辑器右键提供"新建数据库表（向导）"Action
- 3.1.2 表单录入：表中文名、业务描述、用户 NotesID（仅用于服务端归属到所在系统）、字段清单（字段中文名、是否必填、是否主键、长度/精度可选、备注）；"是否主键"为可选勾选，留空时由引擎按 3.2.5 自动补齐主键
- 3.1.3 用户 NotesID 支持本地保存以便复用（仅用于服务端归属系统定位，不作为身份凭证）；插件端不配置 JDBC 连接，数据库连接由服务端按系统维度提供；需配置引擎服务端地址与访问 Token（由服务端签发，见 4.3.1）
- 3.1.4 字段清单支持动态增删行
- 3.1.5 点击"生成 SQL"调用标准引擎（服务端），展示生成结果
- 3.1.6 结果预览：逐字段标注来源徽章（复用·本系统 / 贯标·字典 / 推导·待登记 / LLM·候选 / 需人工复核）；"需人工复核"字段需在预览中显式高亮，允许用户手工修正后再重新生成
- 3.1.7 预览支持人工调整字段定义后"重新生成"
- 3.1.8 提供"复制 SQL"与"插入编辑器"两种落库方式
- 3.1.9 引擎（服务端）不可达或未就绪时给出明确提示，引导用户检查引擎服务状态/网络连通，插件不负责拉起引擎
- 3.1.10 缓存刷新：提供手动刷新入口，触发服务端按当前 NotesID 归属系统刷新本系统 Schema 缓存（见 3.4.2），刷新过程与结果在插件端给出反馈

3.2 标准引擎（后端）
- 3.2.1 提供 POST /generate-ddl 接口：入参为表中文名、描述、用户 NotesID、字段清单（另携带访问 Token，见 4.3.1）；出参为 DDL 文本 + 每字段来源标注（含"需人工复核"标记）+ 待登记字段清单。引擎在 Token 校验通过后按 NotesID 归属系统，采用该系统配置的一个或多个数据库 Schema 作为本系统元数据资源；接口为**单次同步调用**，LLM 辅助（3.5）在服务端同一请求内完成并受超时约束
- 3.2.2 字段命名三级决策与字典取值规则（优先级从高到低）：
  - 3.2.2.1 命中本系统 Schema 缓存（按录入字段中文名与既有字段 COMMENT 中文名**精确匹配**；"同义不同名"不在本期承诺范围，由 3.5 的 LLM 辅助环节识别）→ 直接复用原字段英文名与类型，不再访问贯标标准。本系统元数据按系统维度组织，可由一个或多个数据库 Schema 组成，统一作为"本系统 Schema 缓存"资源参与匹配
  - 3.2.2.2 未命中则查询企业标准字典快照 → 贯标取得标准英文名与标准类型（中文名 → 字典项英文简称/字段名，命名以《数据库设计审核要求》为准：英文字母和自然数加下划线组成、下划线 `_` 分割、长度不超过 30 字符、小写命名，如 `acc_no`；不采用首字母大写的 `Txn_Amt` 形式）
  - 3.2.2.3 两者均未命中 → 按内置缩写词典规则推导命名，标记"待登记"；若中文名含词典未覆盖的词、复合语义，或 COMMENT 为非规整代码清单/脏数据，判定为"规则不能定"，转入 3.5 的 LLM 辅助环节（触发条件见 3.5.2③）
  - 3.2.2.4 重要性分类优先：命中多个字典数据项时，优先选择"公共集"（公司定义标准）；"自治级"（系统自定义）仅在其不存在对应公共集项时采用，且随标准演进逐步被公共级替换
  - 3.2.2.5 存量公共集兼容：已存在的存量公共集数据项（英文简称、类型、格式等）无法更改；新增建表参考公共集时，必须**兼容采用**其既有定义——复用其**选词与下划线结构**（不得自行推导或改写词根），类型与格式同样直接采用；输出时统一转为小写（《数据库设计审核要求》允许与字典英文简称存在大小写差异），以保证新建表与存量标准可继续贯标
- 3.2.3 表名生成：统一以 `t_` 开头（全小写），后续为表中文名称的简称字符串；简称采用**表名专用缩写词典**（按中文词语取拼音首字母/通用简称逐词缩写成型），仅允许小写字母、数字与下划线 `_`，不使用大写与中文字符（如"同业借款合同台账"→ `t_tyjkht`）；表名整体统一小写，长度对齐《数据库设计审核要求》（尽量 ≤32 字节、最大 ≤64 字节；缩写后超出 32 字节按词典规则继续压缩，绝对不超过 64 字节）。表名缩写词典独立维护（见 7.2.1），**不复用字段英文缩写词典**
- 3.2.4 类型映射：中文业务含义/字典标准类型 → 数据库物理类型（含长度/精度默认值）。字典数据项按"数据类型 + 数据格式"推导物理类型，需覆盖：
  - 3.2.4.1 数据类型分类：以《数据库设计审核要求》为准，统一为 10 类——编码类、代码类、标志类、文本类、金额类、数值类、比例类、日期类、时间类、日期时间类；每类映射到目标库物理类型（MySQL/TXSQL 期先支持 VARCHAR/DECIMAL/INT/BIGINT/TINYINT/DATE/DATETIME/TIMESTAMP 等，后续扩展 Oracle/GaussDB 对应类型）
  - 3.2.4.2 数据格式解析：数据格式记号以《数据库设计审核要求》为准（`n6`=6 位数字、`an3`=3 位字母数字、`YYYYMMDD`=日期、`N(2)`=N 位整数 2 位小数等），据此推导长度与精度；对字典中出现的业务口述记法（如 `6!n`=6 位数字、`3!an`=3 位字母数字、`21(2)`=金额）需与标准记法建立映射，统一规则后再解析
  - 3.2.4.3 代码类特殊处理：数据类型为"代码类"时，代码取值与代码名称统一组织为"代码清单"，采用 **JSON 数组** 存储，形如 `[{"code":"0","name":"状态0"},{"code":"1","name":"状态1"}]`，每个元素为"取值 → 名称"键值对（如币种 `{"code":"CNY","name":"人民币"}`）；生成字段时可输出代码清单对应的枚举说明，供建表后维护 CHECK 约束或字典说明。受 MySQL 列注释长度上限（约 1024 字符）约束，代码项过多时 COMMENT 只写摘要与前若干项，**完整代码清单随生成结果单独输出**（或落旁挂代码表），不作静默截断
  - 3.2.4.4 代码类物理类型约束（对齐《数据库设计审核要求》）：代码类字段物理类型采用文本/枚举类型存储编码值（如 VARCHAR），**禁止使用浮点型存储**；字段长度按代码取值设计、不可预留；代码取值仅含数字字母/纯字母，不允许中文字符与特殊字符，且同一码表内取值、名称不重复
- 3.2.5 自动补齐：主键规则（用户已勾选主键时以其为准，否则自动补齐自增 `id` 主键；最终必须且仅有一组主键）、审计字段（CREATE_TIME / UPDATE_TIME 等，由规则表统一列举；用户已录入同名字段时不重复添加）、COMMENT 注释、索引建议（主键索引 + 按字段角色启发式给出的候选列，如编码类/代码类/关联列；**新表无数据，不基于实际选择性计算**，建议结果需用户在预览中确认）；代码类字段 COMMENT 中附加代码清单（JSON 数组）的枚举说明（超长处理见 3.2.4.3）
- 3.2.6 生成"新字段登记清单"：列出所有"推导"字段（含 LLM 候选字段）及其建议英文名，供 BA/数据管理员在字典系统补录；清单字段与该字典数据项结构对齐（字典项编号、中文名称、英文名称、重要性分类、数据类型、数据格式、代码清单），其中**字典项编号对新增项留空**（由管理员登记时生成），不虚构编号
- 3.2.7 系统与连接管理（服务端）：
  - 3.2.7.1 以系统维度维护 JDBC 连接信息（JDBC URL、用户名、密码、数据库类型、Schema 清单），一个系统对应一个或多个数据库 Schema，其元数据同时作为该系统的资源使用；每个系统可有多个开发人员
  - 3.2.7.2 维护用户 NotesID → 所属系统的映射关系
  - 3.2.7.3 生成 DDL 时先校验访问 Token，再按入参 NotesID 反查归属系统，采用该系统配置的全部数据库 Schema 作为本系统元数据资源；Token 无效、NotesID 与 Token 主体不一致或未找到归属时给出明确提示并拒绝访问

3.3 规则集
- 3.3.1 将数据库设计审核要求（物理-表设计 7 项、物理-字段设计 5 项、物理-索引设计 2 项、逻辑-数据项设计 13 项）落为 YAML/JSON 配置
- 3.3.2 规则项包括：表命名规范（`t_` 前缀 + 表中文名简称，全小写）、字段命名规范（表名/字段名 ≤32 字节、最大 ≤64 字节；英文简称 ≤30 字符，即 ≤30 个 ASCII 字符/字节）、表名缩写词典与字段缩写词典（相互独立）、类型映射（含字典数据类型/数据格式 → 物理类型）、**数据格式合法性约束**（日期类仅 `YYYYMMDD`；时间类仅 `HHMMSS`/`HHMMSS.S...S`；日期时间类仅 `YYYYMMDDHHMMSS`/`YYYYMMDDTHHMMSS.S...S`；比例类与金额类仅 `M.N`；数值类不允许 `M(0)`、长度 N 不允许 `n_`；代码类建议 `M_`/`an_`/`anc` 定长且不可预留长度；编码类按编码规则定长且不可预留长度）、必备字段、主键规则（必须含主键、推荐自增 id）、COMMENT 模板、索引默认规则（数量 ≤5，按字段角色启发式建议候选列）、代码类枚举处理规则、重要性分类优先级规则（公共集 > 自治级）、存量公共集兼容规则（复用选词结构、输出小写）
- 3.3.3 物理建表约束（对齐《数据库设计审核要求》）：字符集统一 UTF8MB4、`ENGINE=InnoDB`、不使用外键约束、字段尽量 NOT NULL + 默认值、单表字段数 ≤30、使用 DECIMAL 替代浮点（含小数场景）、避免存储文件对象
- 3.3.4 规则修改不涉及代码改动，重启引擎即生效

3.4 数据缓存
- 3.4.1 本系统 Schema 缓存：由引擎（服务端）直接使用 JDBC 数据库连接获取表结构元数据，服务端 SQLite 落库（启用 WAL 模式，缓存写入串行化）；连接信息**不放在插件端**，而是在服务端**按系统维度统一配置**；一个系统可配置一个或多个数据库 Schema，其元数据同时作为该系统资源落库；插件仅上报用户 NotesID，服务端校验 Token 后据此归属到该系统并采用该系统对应的全部 Schema。SQLite 为 MVP 选型，多开发人员高并发场景下若出现写锁瓶颈，后续再评估切换服务端数据库（本期不做）
- 3.4.2 缓存刷新：引擎启动时基于各系统配置的一个或多个数据库 Schema 自动拉取元数据刷新缓存；插件侧提供手动刷新入口（见 3.1.10），刷新时按当前 NotesID 归属系统刷新该系统对应 Schema，需通过鉴权，不支持刷新其它系统数据
- 3.4.3 企业字典快照：字典系统导出 JSON，**全局维度共用一份**，所有系统、所有开发人员共享同一份字典快照；每个字典数据项含以下字段，人工/脚本导入 SQLite，MVP 不做实时对接：
  - 3.4.3.1 字典项编号：数据项唯一 ID，10 位数字字母字符串
  - 3.4.3.2 字典项中文名称
  - 3.4.3.3 字典项英文名称/英文简称：以《数据库设计审核要求》为准，英文字母和自然数加下划线组成、下划线 `_` 分割、长度不超过 30 字符、小写命名（如 `acc_no`）；该英文简称即数据库字段名
  - 3.4.3.4 重要性分类：公共集 / 自治级（公共集为公司定义标准、优先采用；自治级为系统自定义、逐步缩减并替换为公共级）
  - 3.4.3.5 数据类型：以《数据库设计审核要求》为准，共 10 类（编码类、代码类、标志类、文本类、金额类、数值类、比例类、日期类、时间类、日期时间类）
  - 3.4.3.6 数据格式：以《数据库设计审核要求》为准（如 `n6`、`an3`、`YYYYMMDD`、`N(2)`），业务口述记法（如 `6!n`、`3!an`、`21(2)`）在导入时映射为标准记法
  - 3.4.3.7 代码清单：可选，代码类的全部"代码取值 + 代码名称"，采用 **JSON 数组** 存储，每个元素为 `{"code":"取值","name":"名称"}` 键值对（如 `[{"code":"0","name":"状态0"},{"code":"1","name":"状态1"}]`），取值与名称一一对应并保持一致
  - 3.4.3.8 代码编码规则：可选，"数据类型"为"代码类"时按审核要求本属性为必填项（如"MA 1 做 2 位编码"），用于推导代码类字段的物理长度与格式
  - 3.4.3.9 存量公共集兼容：字典快照中已存在的存量公共集数据项（英文简称、类型、格式等）作为不可变更的标准值，新增建表引用时直接兼容采用（复用其选词与下划线结构，输出统一小写），不得修改或覆盖
- 3.4.4 缓存一致性：本系统 Schema 缓存**按系统维度隔离**，一个系统内的多个 Schema 归为同一系统资源，避免跨系统串数据；企业字典快照为**全局共用一份**，不做系统隔离
- 3.4.5 字典导入方式：MVP 先支持**手动导出**——数据标准部门将字典 JSON 导出后放置到本项目约定目录（如 `config/dict/`），引擎启动时扫描导入 SQLite；后续版本再扩展为系统间自动联动对接

## 3.5 LLM 辅助能力（本期做）

3.5.1 定位：LLM 作为**补充者而非决策主体**，用于处理"确定性规则无法精确判断"的环节（如非规范字段 COMMENT、语义模糊、脏数据），守住"合规、一致、可复现"的核心价值。LLM 任一输出都必须经过确定性规则校验，不确定项标人工复核，绝不静默采用。

3.5.2 处理流程（"逐列取数 + 整体汇总"，规则优先、LLM 兜底）：
```
前端录入表信息/列信息 → 后端
  └─ 遍历每列：
      ① 先跑确定性规则：本系统 Schema 缓存命中 → 字典贯标 → 缩写词典推导
      ② 规则能定 → 直接采用规则结果（快、准、可复现）
      ③ 规则不能定（判定条件：中文名含缩写词典未覆盖的词或复合语义 / COMMENT 为非规整代码清单 / 语义不明或脏数据）
        → 组织该列 Schema 元数据 + 企业标准数据为 LLM 提示
        → LLM 输出候选字段定义（命名/类型/代码清单 JSON）→ 过规则校验
        → 若 LLM 超时或校验不通过，标记"需人工复核"并回退采用规则兜底结果，不阻塞整体生成
  └─ 所有列处理完：
      ④ 规则引擎做合规校验 + 自动补齐（主键/审计字段/索引/审核约束）
      ⑤ （可选）LLM 做整体 DDL 合理性 review，规则引擎最终把关
```

3.5.3 LLM 介入点与职责：
- 3.5.3.1 单列无法精确匹配时（环节③）：LLM 从非规范 COMMENT / 模糊语义解析候选字段定义；规则校验命名合规、类型在 10 类内、代码清单取值合法且可复现
- 3.5.3.2 整体 DDL 生成时（环节⑤）：LLM 对规则生成的 DDL 做合理性 review / 补漏；规则引擎最终把关审核约束、主键、索引等
- 3.5.3.3 COMMENT 规范化：先执行确定性清洗规则（全/半角、空白、分隔符归一、常见模式提取），仅对确定性规则**无法解析**的存量 COMMENT 才调用 LLM 转为标准 JSON；该处理为**离线批量任务**、按批限流执行，不进入在线 /generate-ddl 路径，不受 4.1 在线响应时限约束

3.5.4 铁律（约束）：
- 3.5.4.1 规则优先：所有确定性规则能覆盖的环节，一律不使用 LLM（保性能、保一致、保成本）
- 3.5.4.2 输出必校验：LLM 的任何输出（命名、类型、代码清单）都必须过确定性规则校验
- 3.5.4.3 不确定标复核：LLM 置信度低或规则校验不通过的，标记"需人工复核"，不静默采用
- 3.5.4.4 性能与成本：LLM 调用仅在规则无法决断时发生，避免每列必调；不突破 4.1 性能目标

## 4. 非功能需求

4.1 性能：单次 DDL 生成接口响应 ≤ 2 秒（服务端缓存命中 + 规则可决断场景）；涉及 LLM 辅助（3.5）时放宽至 ≤5 秒，服务端在**同一请求内**完成 LLM 调用并设单列/整体超时上限，超时降级为"需人工复核"（不引入异步回调/轮询，见 3.5.2③）；插件端调用一律异步化、不阻塞 EDT 线程，UI 不卡顿
4.2 兼容性：插件支持行内统一使用的 IDEA **2024.1 及之后新版本**的社区版（Community Edition，构建版本号设定 `sinceBuild` 为 2024.1 稳定版、`untilBuild` 放宽或留空以兼容后续版本）；功能范围内**不依赖仅旗舰版（Ultimate）可用的平台 API**，若后续需引用需降级规避以兼容后续社区版版本；引擎采用 Java，插件采用 Kotlin；本期目标数据库为 MySQL/TXSQL
4.3 安全（引擎服务端集中部署，多开发人员经插件访问）：
- 4.3.1 访问控制：引擎接口**必须**鉴权。插件调用 `/generate-ddl` 时携带用户 NotesID 与访问 Token（Token 由服务端签发、加签并设有效期）；服务端校验 Token 有效性，并校验 NotesID 与 Token 主体、归属系统一致，匹配方可通过；未授权用户拒绝访问。NotesID 仅用于归属定位，**不得单独作为身份凭证**，防止冒用他人 NotesID 越权访问其它系统
- 4.3.2 连接信息安全：服务端集中存储的各系统 JDBC 连接信息（含密码）需加密存储（如加密密钥库），不得明文落盘；密码不出现在日志与接口响应中
- 4.3.3 传输安全：插件与引擎之间通信采用加密传输（内网 HTTPS 或等效加密），避免连接信息、表结构元数据在传输中泄露
- 4.3.4 监听与网络：引擎监听范围从"仅回环"调整为内网可访问，但需限定绑定到内网网卡并配合防火墙白名单，仅允许行内网段访问，不暴露公网
- 4.3.5 数据与日志：日志不记录敏感表数据、连接密码与完整连接串；仅记录必要的操作审计信息（调用用户、时间、动作）
- 4.3.6 LLM 数据安全：发送给 LLM 的提示只包含**必要元数据**（中文名、既有字段英文名/类型/格式等），不含表内业务数据与连接信息；对表名/字段名中的敏感业务信息按规则做别名化或替换后再外发；LLM 服务来源须符合行内合规要求（见 7.2.4）。若合规评估不允许外发库表结构，则 LLM 环节降级为行内本地模型或关闭（本期以 7.2.4 确认结果为准）；LLM 输出不得直接写入生产配置
4.4 可维护性：规则集与代码分离，配置化维护；引擎与插件独立升级
4.5 分发：插件 zip 通过"Install Plugin from Disk"或内部私有 Marketplace 分发到各开发人员；引擎作为服务端集中部署，提供部署包/启动脚本（Windows/Linux 均可）并支持配置引擎地址与鉴权参数

## 5. 验收标准

5.1 向导从表单录入到生成合规 DDL 全流程可用：新建一张 10 字段的表，字段来源覆盖"复用/贯标/推导"三类并正确标注；若触发 LLM 或人工复核，相应字段正确标注"LLM·候选"/"需人工复核"
5.2 生成的 DDL 通过行内数据库设计审核规则自检（命名、类型、主键、审计字段、注释齐全）
5.3 本系统已有字段（录入中文名与既有字段 COMMENT 中文名精确匹配）复用时不再触发字典贯标（验证"本系统优先"策略生效）；"同义不同名"由 LLM 辅助环节识别，不作为本期复用承诺
5.4 字典数据项正确应用：英文名称格式（下划线 `_` 分割、小写、长度 ≤30 字符）、数据类型/数据格式映射到物理类型、公共集优先于自治级且存量公共集被兼容采用（复用其选词与下划线结构、输出统一小写），均符合字典标准与《数据库设计审核要求》
5.5 代码类字段：代码清单以 JSON 数组存储，取值与名称一一对应一致，物理类型为文本/枚举且禁止浮点存储，COMMENT/CHECK 说明可正确输出
5.6 推导字段能正确输出"待登记清单"，格式（字典项编号留空、中文/英文名、重要性分类、数据类型、数据格式、代码清单）可供数据管理员直接使用，不虚构字典项编号
5.7 系统与连接归属正确：插件录入用户 NotesID 后，服务端能归属到所属系统，并采用该系统配置的一个或多个数据库 Schema 拉取元数据；未配置归属时给出明确提示
5.8 多 Schema 资源：一个系统可配置多个数据库 Schema，其元数据同时作为该系统资源参与本系统 Schema 缓存匹配，不跨系统串数据
5.9 字典全局共用：企业字典快照为全局维度一份，不同系统、不同用户贯标查询结果一致
5.10 插件端不配置任何 JDBC 连接信息，连接完全由服务端按系统维度管理
5.11 引擎（服务端）不可达或鉴权失败时，插件给出友好提示且不崩溃
5.12 LLM 辅助生效：当规则无法精确决断（非规整代码清单/语义不明）时，LLM 能给出候选字段定义，且结果通过确定性规则校验；规则能决断时不触发 LLM 调用
5.13 LLM 输出受控：LLM 输出命名合规、类型在 10 类内、代码清单取值合法；低置信或校验不通过的标记"需人工复核"，不静默采用
5.14 LLM 数据安全：发送给 LLM 的提示已完成脱敏，无真实敏感数据/连接信息泄露
5.15 典型场景演示：同业借款合同台账建表，全流程 ≤ 3 分钟
5.16 性能达标：缓存命中 + 规则可决断场景下 `/generate-ddl` 响应 ≤ 2 秒；LLM 场景 ≤ 5 秒，超时或低置信结果按 3.5.2③ 正确降级为"需人工复核"，插件 UI 不卡顿
5.17 安全达标：未携带或伪造 Token、NotesID 与 Token 主体不一致时被拒绝访问；服务端 JDBC 密码加密存储，日志与接口响应中不出现密码或完整连接串
5.18 可维护性达标：修改规则配置（§3.3）后重启引擎即生效，无需改动代码
5.19 分发达标：插件 zip 可通过"Install Plugin from Disk"在 IDEA 2024.1 及之后社区版正常安装使用；引擎部署包可在 Windows/Linux 启动

## 7. 已确定决策与待确认事项

### 7.1 已确定决策
- 7.1.1 引擎技术栈：**Java**（团队同栈）
- 7.1.2 插件语言：**Kotlin**（IntelliJ 官方插件开发生态首选，配合引擎 Java 通过 HTTP 通信）
- 7.1.3 数据库类型支持规划：**MVP 第一期支持 MySQL 及其兼容体系 TXSQL**（MYSQL/TXSQL 体系，二者语法与物理类型兼容），后续版本再扩展支持 Oracle、GaussDB；DDL 生成、类型映射、JDBC 元数据拉取按数据库类型做扩展点设计
- 7.1.4 企业字典快照获取方式：MVP 第一期先支持**手动导出**——数据标准部门导出字典 JSON 后放置到本项目约定目录，引擎启动时扫描导入；后续版本再扩展支持系统间自动联动对接（详见 3.4.5）
- 7.1.5 企业字典快照的导出方：**数据标准部门可提供** JSON 导出，导出内容包含字典项编号、中文/英文名称、重要性分类、数据类型、数据格式、代码清单（JSON 数组）等完整字段
- 7.1.6 JDBC 连接方式：**不在插件端配置**；以**系统维度**在服务端统一配置 JDBC 连接（一个系统可对应一个或多个数据库 Schema，元数据同时作为该系统资源，可含多个开发人员）；插件录入用户 NotesID（仅用于归属定位），服务端维护 NotesID → 系统归属，并在 Token 校验通过后采用该系统对应的全部 Schema（详见 3.2.7、3.4.1、4.3.1）
- 7.1.7 数据维度：本系统 Schema 元数据**按系统维度**组织（一系统可含多 Schema）；企业数据字典为**全局维度**，所有系统/所有人共用一份
- 7.1.8 目标 IDEA 版本能力：企业统一使用 **2024.1 及之后新版本**的社区版，已确认功能范围内**不依赖仅旗舰版（Ultimate）可用的平台 API**，且需兼容后续社区版版本的 API 变更（插件开发遵循此约束）
